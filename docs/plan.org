*** PLANNED Upgrade system
+ The modifiers defined now need to be tied into the upgrade system. Uprades are very open ended for now. They can be of multiple types:  
  + Permanent modifiers to the game like increased rate of energy etc.
  + Special objects like Dense Iron cores (or other new celestial objects),  and entirely new mechanics like energy harnessers, gravity wells. Each of these items will have completely custom behaviour
+ We need to think of more interesting upgrade paths and mechanics. For now, we want to make sure our architecture is scalable.
+ The system needs to support unlock conditions and have a gradual tiered unlock system.
+ Design: [[file:upgrade-system.org]], decisions: [[file:adr/0006-upgrade-system.org]],
  vocab: [[file:glossary.org]]. Amends [[file:adr/0005-modifier-system.org]].
+ Upgrade *levels* are the source of truth (=upgrade_levels[Upgrade_Id]u8=);
  upgrades never create Modifiers. Multi-level nodes with per-node =max_level=.
+ Three effect classes: Param (folded into effective_params), Capability
  (derived =bit_set=), Grant (monotonic write at purchase). DAG prereqs via
  4 =requires= slots (arrays, not =bit_set=, so node count is uncapped).
+ Monotonic-only unlock conditions (no stored =revealed= latch): lifetime energy
  earned, celestial discovered, upgrades purchased.
+ =sys_modifier= absorbs upgrades and becomes the single derive pass (also runs
  while =.Paused=); ops in NEW =upgrades.odin= + =economy.odin=. Structure in
  compile-time =UPGRADE_DEFS=, balance in =Parameters.upgrades= (unpersisted).
+ v1: 12 Run nodes + 1 Meta placeholder. 4 phases: engine → menu → wiring →
  balance/persistence. Save payload changes without a version bump (pre-release).
